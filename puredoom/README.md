# puredoom

[PureDOOM](https://github.com/Daivuk/PureDOOM) (Daivuk's embeddable Doom, GPL-2) at `355cfbd16fac119718879239336ee2ea408886bd`, patched, converted to daslang by [c2das-re](https://github.com/lookibed/c2das-re): the 62 C files of `src/DOOM/` and c2das-re's headless host `doom/host/doom_main.c`, which holds `main`. Everything in this directory is generated by `scripts/publish_ports.sh --program puredoom` in c2das-re; never edit it, a fix belongs in c2das-re.

## Files

- `doom/` - the program as a module per C file, every cycle of files one module of `.das.inc` fragments (c2das-re's source layout; `doom/program.layout.txt` lists the modules); `doom/doom_main.das` holds `main`.
- `doom.c2das` - the sidecar the conversion ran under.
- `patches/` - the patches c2das-re applies to the pinned commit before converting it.
- `LICENSE` - PureDOOM's license, the GNU GPL version 2; the conversion and the patches are distributed under it.

## Source

- Upstream: https://github.com/Daivuk/PureDOOM at `355cfbd16fac119718879239336ee2ea408886bd`, with c2das-re's patches applied in order:
  - `0001-per-tic-checksum.patch` - c2das-re instrumentation of PureDOOM, applied by doom/fetch.sh to the commit VERSIONS.md pins. g_game.c: with -DDOOM_TIC_CHECKSUM, G_Ticker ends by storing the tic it ran and its checksum, the 32-bit FNV-1a (offset basis 2166136261, prime 16777619) over the little-endian bytes of players[0].mo->x, y, z, angle (0 without a mobj), players[0].health and prndindex, the index P_Random steps. d_main.c: with the define, D_DoomLoop prints one line per game tic once D_Display has drawn it, "tic=<gametic> cs=<8 hex digits> fb=<8 hex digits>", fb the same FNV-1a over the bytes of screens[0]. Without the define the build prints nothing more. w_wad.c, r_data.c, i_video.c: a cached lump ends in 128 zero bytes, a composite texture is zeroed with the same slack, and the screen starts zeroed. A column drawer reads up to 127 bytes past a column's start (a wall taller than its texture, a post's first row rounded to row -1 and wrapped to 127), which past a lump's end read the zone's next block header, so the frame of such a tic changed from run to run with the heap's addresses. d_main.c: -playdemo and -timedemo return from D_DoomMain after I_InitGraphics. PureDOOM's D_DoomLoop runs a single tic and returns, so the call vanilla never returns from fell through to the title loop (or, for a multiplayer demo, to G_InitNew), which replaced the demo.
  - `0002-tic-trace.patch` - c2das-re trace of PureDOOM's tic checksum, applied by doom/fetch.sh after 0001. p_tick.c: with -DDOOM_TIC_TRACE, P_Ticker ends by printing one line per level tic, "trace=<gametic> x=<hex> y=<hex> z=<hex> ang=<hex> hp=<d> prnd=<d>", the six values the per-tic checksum hashes. Without the define the build prints nothing more; no reference log is recorded with it.
  - `0003-signed-ticcmd.patch` - c2das-re fix of PureDOOM's ticcmd_t, applied by doom/fetch.sh after 0001. d_ticcmd.h: ticcmd_t's forwardmove and sidemove are `signed char`, as in Chocolate Doom. A demo stores a backward or leftward move as a negative byte, which G_ReadDemoTiccmd casts to `signed char`; in a plain `char` field it reads back negative only where `char` is signed. The converter's dialect is unsigned `char` (docs/probe-findings.md F17), so a plain field read the -40 of a strafe as 216.
  - `0004-fine-table-overruns.patch` - c2das-re fix of PureDOOM's fine-table overruns, applied by doom/fetch.sh after 0001. r_main.c, r_segs.c: R_ScaleFromGlobalAngle indexes finesine by an int angle that goes negative past ANG180, and R_RenderSegLoop indexes finetangent up to 8191, past its 4096 entries. tables.c defines finetangent right before finesine, so the native build reads the neighbouring table; the patch spells those reads out, the same values, so a build that range-checks its arrays (the converted one) reads them too.
- Generated by c2das-re `v0.5.0-673-gce19ef3` (`ce19ef3bfeff77c3f9964e6e9067c1060a148572`, committed 2026-11-12)

## Game data

No WAD is published here. The demos run on `freedoom2.wad` of Freedoom (BSD), 0.13.0 (the freedoom release https://github.com/freedoom/freedoom/releases/download/v0.13.0/freedoom-0.13.0.zip (sha256 3f9b264f3e3ce503b4fb7f6bdcb1f419d93c7b546f4df3e874dd878db9688f59), the latest on 2026-11-02, and its `freedoom2.wad` (sha256 a8772e088847032510d97ba2312406a6998f21cbab44d4ff10696faa9c0ecd4b); `doom/fetch.sh` downloads the zip, checks both hashes and extracts the wad into `doom/fetch/wads/`). c2das-re's `doom/fetch.sh` clones PureDOOM at the pin, applies the patches, downloads that release, checks both hashes and extracts the wad into `doom/fetch/wads/`. PureDOOM opens `$DOOMWADDIR/doom2.wad`, so a run links the wad under that name in its own folder.

## Running

The modules require c2das-re's `crt` and `c_runtime` modules: a c2das-re checkout at the commit above, with the daScript its `VERSIONS.md` pins built, `scripts/build_crt.sh` run and `doom/fetch.sh` run. With `<c2das-re>` that checkout:

```
mkdir run && ln -s <c2das-re>/doom/fetch/wads/freedoom2.wad run/doom2.wad
DOOMWADDIR=run daslang -load_module <c2das-re>/dasCRuntime -load_module <c2das-re>/c_runtime doom/doom_main.das -- -timedemo demo1
DOOMWADDIR=run daslang -load_module <c2das-re>/dasCRuntime -load_module <c2das-re>/c_runtime -jit doom/doom_main.das -- -timedemo demo1
daslang -load_module <c2das-re>/dasCRuntime -load_module <c2das-re>/c_runtime -exe doom/doom_main.das -output doom_exe && DOOMWADDIR=run ./doom_exe -timedemo demo1
# the native build the tables compare with, in <c2das-re>:
daslang -load_module dasCRuntime -load_module c_runtime doom/run.das -- --native
```

Everything after `--` is the program's own command line; the program plays the demo headless and ends with `timed N gametics`.

Box PC (AMD Ryzen 7 7435HS), linux x86_64; c2das-re `3259e3b46569`, captured 2026-11-09 18:10 UTC; clang version 22.1.8 (https://github.com/llvm/llvm-project ca7933e47d3a3451d81e72ac174dcb5aa28b59d1); daslang 0.6.5.

PureDOOM `-timedemo demoN` on freedoom2.wad. fps is the demo's gametics over the process CPU time (`clock()`) of the host's update loop in the speed build, which leaves the patch's per-tic checksums and tic lines out: the playback alone, the module load, the JIT compile and `doom_init` outside it. Per demo and lane one run of the sync build first holds every tic to the reference log; a cell is then the median of 5 speed runs, each its own process ending in the demo's `timed N gametics`, ± half the range over the median; above 20% it is `suspect`, without a ratio. `X / native` is native fps over X's.
